# Network Security Practice — DNS Exfiltration PCAP

**Category:** Network Security / Forensics  
**Technique:** DNS traffic analysis and encoded-data detection  
**Difficulty:** Medium  
**Type:** Self-Created Practice Lab

> This is an original CTF-style practice scenario created for learning. It is not an official CTF challenge and does not represent a real solved challenge, flag, ranking, or achievement.

## Challenge / Context

A small lab network capture contains normal DNS traffic mixed with requests generated by a simulated compromised host. The objective is to identify the suspicious DNS activity and recover the non-sensitive lab message carried in the query labels.

The scenario is intentionally self-contained. No real credentials, secrets, or production data are used.

## Reconnaissance / Analysis

Start by checking the capture and identifying the protocols involved.

```bash
capinfos capture.pcap
```

Then inspect DNS packets:

```bash
tshark -r capture.pcap -Y 'dns' \
  -T fields -e frame.number -e ip.src -e dns.qry.name
```

Look for patterns such as:

- Many DNS queries from the same internal host
- Repeated queries to one unusual subdomain
- Long labels compared with normal hostnames
- Labels containing mostly hexadecimal or Base32-like characters
- Sequential-looking query fragments

A single unusual DNS request is not enough to establish exfiltration. The useful signal is the combination of **frequency, label length, repeated destination, and encoded-looking data**.

## Vulnerability / Technique

The practice scenario demonstrates **DNS tunneling / DNS-based data exfiltration**.

DNS is normally used for name resolution, but an attacker can encode small pieces of data inside query names and send many requests to an attacker-controlled domain. DNS itself does not make the embedded data malicious; the analyst has to correlate traffic patterns and inspect the payload structure.

The analysis flow is:

```text
PCAP
 ↓
Protocol filtering
 ↓
Identify repeated DNS destination
 ↓
Inspect query labels
 ↓
Extract suspicious labels
 ↓
Reassemble ordered fragments
 ↓
Decode the lab data
```

## Solution Steps

### 1. Filter DNS traffic

In Wireshark, use:

```text
dns
```

Or with `tshark`:

```bash
tshark -r capture.pcap -Y 'dns.qry.name' \
  -T fields -e frame.number -e ip.src -e dns.qry.name
```

### 2. Find repeated destinations

Group queries by the queried domain:

```bash
tshark -r capture.pcap -Y 'dns.qry.name' \
  -T fields -e dns.qry.name | sort | uniq -c | sort -nr
```

A domain receiving many queries from one host is worth investigating, especially when the left-most label changes on every request.

### 3. Extract suspicious labels

For a lab domain such as `data.lab`, isolate the query names and inspect the changing portion.

```bash
tshark -r capture.pcap -Y 'dns.qry.name contains "data.lab"' \
  -T fields -e frame.number -e dns.qry.name
```

Preserve packet order when extracting fragments. Ordering matters because each query may contain only one piece of the message.

### 4. Check the encoding

If the labels contain characters consistent with Base32, remove the lab domain and concatenate the fragments in packet order.

A simple Python decoder for a controlled Base32 sample is:

```python
import base64

encoded = "".join(fragments)
message = base64.b32decode(encoded + "=" * ((8 - len(encoded) % 8) % 8))
print(message.decode(errors="replace"))
```

Do not assume that every long DNS label is Base32. Validate the character set, padding requirements, and decoded output against the observed traffic.

### 5. Validate the finding

Compare the suspicious traffic with ordinary DNS queries in the same capture. The key indicators are the repeated destination, unusually structured labels, and sequential fragments that reconstruct meaningful lab data.

A robust analysis should also check the source host and timestamps rather than relying only on the decoded message.

## Result

In this self-created practice lab, the analyst identifies a simulated DNS exfiltration channel and reconstructs the intentionally non-sensitive lab message from ordered encoded query fragments.

The exercise demonstrates the investigation technique without using a real compromised system, credential, secret, or official CTF flag.

## Lessons Learned

- DNS can be abused as a low-bandwidth data transport channel.
- Traffic volume, repeated destinations, label length, and encoding patterns are useful detection signals.
- Packet ordering is important when reconstructing fragmented data.
- Encoded-looking data is not automatically malicious; context and correlation are required.
- Network analysis should preserve source, destination, timing, and protocol context instead of examining payloads in isolation.

## Defensive Considerations

For environments where DNS exfiltration is a concern:

- Centralize DNS resolution where practical.
- Log DNS queries and retain enough metadata for investigation.
- Alert on unusually long or high-entropy labels and abnormal query rates.
- Restrict unauthorized direct DNS access from endpoints.
- Correlate DNS anomalies with endpoint and network telemetry.

## Conclusion

This practice lab demonstrates a realistic network-forensics workflow for recognizing DNS-based exfiltration in a packet capture. The main skill is not simply decoding a string; it is building enough evidence from DNS behavior to distinguish an unusual query pattern from normal name resolution.
